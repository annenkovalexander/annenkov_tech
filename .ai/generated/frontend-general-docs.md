Данное приложение предназначено для визуализации и управления списками событий, распределенных по временным периодам. Основные сценарии включают просмотр карточек событий, навигацию между страницами данных и управление временными интервалами через контроллеры интерфейса.

Архитектура фронтенда разделяет ответственность между слоями представления и бизнес-логики. Интерфейс состоит из переиспользуемых UI-компонентов и структурных элементов: списков событий и элементов управления периодами. Слой сервисов обеспечивает взаимодействие с внешним API для получения данных о событиях и содержит инструменты для работы с состоянием экрана.

Глобальное состояние реализовано с помощью Redux. Используются отдельные слайсы для хранения профиля пользователя в заголовке (имя, роль), управления данными периодов и отслеживания активного интервала. Доменными сущностями являются события и временные периоды.

# Архитектура фронтенда

## Общая структура

Архитектура построена на разделении ответственности между уровнями представления, управления состоянием и сетевого взаимодействия. Логика получения и обработки данных изолирована от их визуализации.

## Интерфейсные слои

Верхний уровень представлен страницами-координаторами. Они формируют экраны из функциональных модулей и определяют композицию элементов.

Средний слой состоит из переиспользуемых компонентов: списков событий, элементов пагинации и контроллеров управления временными интервалами. Эти блоки содержат локальную логику взаимодействия, навигации и фильтрации данных. 

Нижний уровень представляет собой библиотеку базовых UI-элементов (атомарных компонентов), обеспечивающих визуальный стиль приложения.

## Данные и состояние

Состояние организовано централизованно в двух областях:
*   **Профиль пользователя**: персональные данные и уровень доступа для отображения в заголовке.
*   **Управление периодами**: доступные временные интервалы, текущий активный период и заголовок страницы.

При смене временного интервала через контроллеры интерфейса обновляется глобальное состояние, что приводит к перерисовке списка событий и связанных текстовых элементов.

## Сетевое взаимодействие и сервисы

Запросы к внешнему API вынесены в сетевой слой. Он отвечает за получение данных о событиях через сервисные функции. Асинхронная логика загрузки отделена от компонентов отображения. В слое сервисов также реализованы хуки для работы с параметрами экрана.

## Основные пользовательские сценарии

### Просмотр и навигация по событиям
Пользователь взаимодействует со списком событий в виде карточек. Для переключения между страницами списка используется система пагинации.

### Управление временными интервалами
Смена временного периода осуществляется через специализированные контроллеры управления. Переключение активного интервала обновляет набор отображаемых данных и заголовок страницы.

### Работа с данными профиля
В верхней части интерфейса отображается информация об аккаунте пользователя: полное имя, роль и описание.

## Данные и взаимодействие с backend

## Типы данных и контракты
Используются три доменные сущности: события, временные периоды и профиль пользователя. Профиль включает полное имя, роль в системе и описание. Данные о периодах и событиях используются для фильтрации и визуализации контента.

## Состояние и асинхронные операции
Глобальное состояние разделено на две области: 
*   **Профиль пользователя**: данные текущего авторизованного пользователя (`fullName`, `role`, `description`) для отображения в заголовке.
*   **Управление периодами**: список доступных интервалов, идентификатор активного периода и заголовок страницы.

Данные предоставляются компонентам через селекторы. Изменения состояния инициируются действиями пользователя или результатами сетевых запросов.

## API и синхронизация
Взаимодействие с backend реализовано в сетевом слое через сервисы, например `getEvents`. Эти функции загружают списки событий для выбранного временного интервала. Полученные данные записываются в состояние приложения, после чего обновляются карточки событий и элементы навигации.

## Поддержка пользовательских потоков
*   **Просмотр событий**: получение и отображение списка событий с пагинацией через вызовы API и состояние периодов. 
*   **Смена временных интервалов**: обновление активного периода в состоянии -> запрос новых данных -> обновление контекста страницы. 
*   **Идентификация пользователя**: доступ к данным о роли и имени пользователя через отдельный слайс профиля во всех частях интерфейса, включая хедер.

## Страницы и основные интерфейсные блоки

### Основные страницы

Основная страница (главный экран) служит единым интерфейсом для просмотра списка событий, управления временными интервалами и доступа к данным профиля пользователя.

### Крупные интерфейсные блоки

*   **Шапка (Header)**: отображение полного имени и роли пользователя.
*   **Список карточек событий (EventCardList) и отдельные карточки (EventCardUI)**: визуализация информации о событиях.
*   **Контроллеры периодов (PeriodControls) и заголовок периода (PeriodTitle)**: выбор временного интервала и отображение его названия.
*   **Панель пагинации (Pagination)**: переключение между страницами списка событий.
*   **Графические элементы (Circle, Dot, Rectangle, SVGLine)**: визуальное оформление контента.

### Связь с пользовательскими сценариями

В сценарии навигации по событиям используются блок списка карточек и панель пагинации. Сценарий управления интервалами реализуется через контроллеры периодов; это обновляет список событий и заголовок периода. Работа с профилем ограничена областью шапки приложения. Все блоки интегрированы в общий макет страницы.

## Особенности технической реализации

Архитектура разделяет ответственность между страницами, переиспользуемыми компонентами и базовыми UI-элементами. Страницы координируют сборку экранов из модулей. Сервисный слой отвечает за взаимодействие с API и предоставляет вспомогательные инструменты.

Доменные сущности (события, временные периоды, профиль пользователя) описаны отдельными типами данных. Эти структуры используются для согласованного описания информации в приложении.

Состояние разделено по тематическим областям: данные профиля и управление периодами. Компоненты используют селекторы для получения данных из этих областей. Изменения состояния инициируются действиями пользователя или сетевыми запросами.

API-слой содержит функции загрузки списков событий. Сетевые операции отделены от представления и состояния приложения. 

## Расширение и сопровождение

Добавление новых интерфейсных решений осуществляется через существующие уровни:
*   новые экраны -> страницы;
*   переиспользуемые блоки -> виджеты;
*   логика пользовательских действий -> функциональные модули.

Расширение предметной области происходит через добавление или уточнение доменных типов. Новые API-операции связываются с асинхронной логикой и соответствующими областями состояния. 

При изучении проекта рекомендуется следующий порядок: доменные типы -> API-операции -> состояние -> селекторы. Путь данных в системе выглядит так: сетевая операция -> асинхронная логика -> состояние -> компоненты интерфейса (через селекторы).
