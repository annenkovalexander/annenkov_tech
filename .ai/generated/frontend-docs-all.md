Приложение предназначено для визуализации и навигации по событиям в рамках временных периодов. Основные сценарии включают просмотр списка событий через карточки, переключение между временными отрезками с помощью пагинации и управление отображением текущего периода.

Архитектура фронтенда основана на послойном принципе: уровень страниц, библиотека общих UI-компонентов и слой сервисов. Взаимодействие с бэкендом реализовано через API-сервисы для получения данных о событиях.

Управление состоянием приложения осуществляется с помощью Redux. Состояние разделено на функциональные слайсы: данные заголовка (сведения о пользователе и его роли) и данные периодов (активный отрезок времени, заголовок страницы).

# Ошибки и проблемы

### 1. Некорректная регистрация хука как плагина GSAP
- **Приоритет:** Medium
- **Тип:** подтверждённая ошибка
- **Что обнаружено:** Функция `useGSAP` регистрируется через `gsap.registerPlugin`.
- **Почему это важно:** `useGSAP` является React-хуком из пакета `@gsap/react`, а не плагином GSAP. Метод `registerPlugin` предназначен для расширения функционала ядра GSAP (например, `MotionPathPlugin`). Попытка зарегистрировать хук как плагин приведет к ошибке в консоли или некорректному поведению библиотеки.
- **Сценарий проявления:** При инициализации приложения и загрузке компонента `Circle`.
- **Необходимые условия:** Запуск кода в среде с установленным `@gsap/react` и `gsap`.
- **Как исправить или проверить:** Удалить строку регистрации для хука. Оставить регистрацию только для `MotionPathPlugin`.
- **Дословный фрагмент:**
```text
gsap.registerPlugin(useGSAP);
```

### 2. Отсутствие управления жизненным циклом анимаций (Race Condition)
- **Приоритет:** High
- **Тип:** условный риск
- **Что обнаружено:** В функции `handleDotClick` создаются новые анимации `gsap.to` для каждого элемента без предварительной остановки текущих анимаций через `gsap.killTweensOf`.
- **Почему это важно:** Если пользователь быстро нажмет на разные точки или если `useEffect` сработает несколько раз за короткий промежуток времени (из-за смены `currentPeriod`), на одном и том же DOM-элементе будут одновременно запущены несколько конфликтующих анимаций. Это приведет к «дрожанию» элементов, визуальным артефактам и непредсказуемому конечному положению точек.
- **Сценарий проявления:** Быстрое переключение периодов пользователем или частая смена `currentPeriod` в Redux.
- **Необходимые условия:** Наличие активной анимации в момент запуска новой.
- **Как исправить или проверить:** Перед запуском цикла с `gsap.to` вызвать `gsap.killTweensOf(element.element)`.

### 3. Использование императивных слушателей событий вместо React-пропсов
- **Приоритет:** Medium
- **Тип:** вопрос к архитектуре
- **Что обнаружено:** Обработчики кликов добавляются вручную через `addEventListener` внутри хука `useGSAP`.
- **Почему это важно:** Это нарушает декларативную модель React. Компонент `DotUI` получает реф, но не получает пропс `onClick`, что делает его менее переиспользуемым и затрудняет тестирование. Также ручное управление слушателями повышает риск утечек памяти при некорректном удалении в cleanup-функции (хотя здесь cleanup реализован).
- **Сценарий проявления:** При разработке или рефакторинге компонента `DotUI`.
- **Необходимые условия:** Наличие доступа к DOM через рефы.
- **Как исправить или проверить:** Передать функцию `handleDotClick` в компонент `DotUI` как пропс `onClick` и вызвать её внутри `DotUI`.

### 4. Риск использования Non-null Assertion (`!`) для PathRef
- **Приоритет:** Medium
- **Тип:** условный риск
- **Что обнаружено:** Внутри `handleDotClick` используется оператор `!`, когда передается путь для анимации в GSAP.
- **Почему это важно:** Хотя в начале компонента есть проверки, `handleDotClick` может быть вызвана в моменты, когда `pathRef.current` еще не инициализирован или уже очищен (например, при быстром размонтировании/монтировании). Это приведет к Runtime Error (TypeError), так как GSAP попытается прочитать свойства у `null`.
- **Сценарий проявления:** Вызов анимации до полной отрисовки SVG или в момент размонтирования.
- **Необходимые условия:** Отсутствие значения в `pathRef.current` в момент срабатывания колбэка.
- **Как исправить или проверить:** Заменить `!` на проверку `if (!pathRef.current) return;`.
- **Дословный фрагмент:**
```text
motionPath: {
    path: pathRef.current!,
    align: pathRef.current!,
```

# Улучшения

### Архитектура и расчеты
- **Вынос «магических чисел»:** Код содержит множество жестко заданных констант (`1440`, `530`, `720`, `480`). Рекомендуется вынести их в отдельный конфигурационный объект или константы (например, `DESIGN_WIDTH = 1440`), чтобы упростить поддержку адаптивности.
- **Оптимизация `getNewPositions`:** Функция пересчитывает позиции при каждом клике. Логику расчета дельты и новых позиций можно упростить, используя модульную арифметику более эффективно.

### Типизация
- **Типизация RefElement:** В текущем коде используется `HTMLDivElement`. Если в будущем `DotUI` изменит корневой элемент на другой (например, `button`), потребуется менять типы во всем файле. Рекомендуется использовать более общий тип или интерфейс.

### Стиль
- **Использование `Number()` для сравнения:** В коде встречается приведение типов при сравнении: 
```text
isActive={Number(currentPeriod) === Number(period.periodId)}
```
Если типы в Redux определены как строки, лучше привести их к одному типу один раз при получении данных, а не при каждом рендере каждой точки в цикле `.map()`.

## Ошибки и проблемы

### 1. Риск неопределённых значений при расчёте списков годов
- **Приоритет:** High
- **Тип:** подтверждённая ошибка
- **Что обнаружено:** В рендеринге компонента используются неконтролируемые приведения типов через оператор `!`. Несмотря на проверку `if (yearsData)`, свойства `startYear` и `endYear` внутри объекта могут отсутствовать.

### 2. Противоречивое использование non-null assertion и nullish coalescing
- **Приоритет:** Medium
- **Тип:** подтверждённая ошибка
- **Что обнаружено:** В `useEffect` используется конструкция, где оператор `!` (утверждение о том, что значение не null/undefined) стоит перед оператором `??` (обработка случая, если значение null/undefined).
- **Почему это важно:** Это логическое противоречие. Оператор `!` говорит компилятору «игнорируй возможность undefined», а оператор `??` говорит «если здесь undefined, используй 2026». С точки зрения runtime, `!` ничего не делает, но с точки зрения чистоты кода это свидетельствует о неправильной работе с типами.
- **Сценарий проявления:** Статическая проверка типов; затруднение поддержки кода.
- **Необходимые условия:** Анализ исходного кода.
- **Как исправить или проверить:** Удалить `!`, так как `??` уже обеспечивает безопасность и предоставляет значение по умолчанию.
- **Дословный фрагмент:**
```text

year2Old.current = yearsData?.endYear! ?? 2026;
```

- **Тип:** вопрос к архитектуре

## Ошибки и проблемы

### 1. Отсутствие единиц измерения в CSS-свойствах
- **Приоритет:** High
- **Тип:** подтверждённая ошибка
- **Что обнаружено:** В объекте `style` для свойств `top` и `left` используются шаблонные строки, которые передают только числовое значение без указания единиц измерения (например, `px`).
- **Почему это важно:** Согласно спецификации CSS, числовые значения в свойствах позиционирования (кроме 0) должны иметь единицы измерения. Браузер проигнорирует такие значения как невалидные, и элемент будет всегда отображаться в точке (0,0) относительно родителя.
- **Сценарий проявления:** При любом значении `x` или `y`, отличном от нуля, прямоугольник не сдвинется с верхнего левого угла контейнера.
- **Необходимые условия:** Рендеринг компонента в браузере.
- **Как исправить или проверить:** Добавить единицы измерения (например, `${x}px`) к значениям `top` и `left`.
- **Дословный фрагмент:**
```text
<div style={{position: "absolute", top: `${x}`, left: `${y}`}}>
```

### 2. Инверсия осей координат (X/Y)
- **Приоритет:** High
- **Тип:** подтверждённая ошибка
- **Что обнаружено:** Переменная `x` (обычно отвечающая за горизонтальную ось) присвоена свойству `top`, а переменная `y` (вертикальная ось) — свойству `left`.
- **Почему это важно:** Это нарушает общепринятую систему координат в веб-разработке и графике, где X соответствует горизонтали (Left), а Y — вертикали (Top).
- **Сценарий проявления:** При попытке сместить объект по оси X (вправо), он будет смещаться вниз. При попытке сместить по оси Y (вниз), он будет смещаться вправо.
- **Необходимые условия:** Передача значений `x` и `y` в компонент.
- **Как исправить или проверить:** Поменять свойства местами: `left: `${x}px`, top: `${y}px`.
- **Дословный фрагмент:**
```text
<div style={{position: "absolute", top: `${x}`, left: `${y}`}}>
```

### 3. Двойное смещение координат (Double Offset)
- **Приоритет:** High
- **Тип:** подтверждённая ошибка
- **Что обнаружено:** Координаты `x` и `y` используются дважды: первый раз для позиционирования внешнего `div` через CSS (`top`/`left`), второй раз — внутри SVG в атрибутах тега `<rect>` (`x` и `y`).
- **Почему это важно:** Внешний `div` с `position: absolute` уже смещает всю область SVG. Атрибуты `x` и `y` внутри `<rect>` смещают сам прямоугольник относительно начала координат этого SVG. В итоге итоговое положение прямоугольника на экране будет равно $(x + x)$ по горизонтали и $(y + y)$ по вертикали.
- **Сценарий проявления:** Прямоугольник окажется в два раза дальше от края страницы/контейнера, чем ожидалось по переданным пропсам.
- **Необходимые условия:** Передача ненулевых значений `x` и `y`.
- **Как исправить или проверить:** Либо оставить позиционирование только на уровне внешнего `div` (установив `x={0} y={0}` в `<rect>`), либо использовать только атрибуты SVG, убрав стили с `div`.
- **Дословный фрагмент:**
```text
<div style={{position: "absolute", top: `${x}`, left: `${y}`}}>
            <svg
                xmlns="http://www.w3.org/2000/svg"
                width={width}
                height={height}
                viewBox={`0 0 ${width} ${height}`}
            >
                <rect

                    y={y}
```

- **Приоритет:** Medium

- **Как исправить или проверить:** Добавить `.catch()` в цепочку вызовов для обработки ошибки и обновления состояния `error` (которое уже объявлено в компоненте) и `status`.

## 1. Хранение данных о событиях внутри состояния периодов

- **Приоритет:** Medium
- **Тип:** вопрос к архитектуре
- **Что обнаружено:** Селектор `getEventsList` извлекает список событий напрямую из объекта периода, находящегося в состоянии слайса:
```text
        getEventsList: (state: AppState) => {
            const foundPeriod = getPeriodById(state);
            return foundPeriod?.events ?? [];
        },
```
- **Почему это важно:** Согласно документации, приложение предназначено для визуализации событий, и взаимодействие с бэкендом реализовано через API-сервисы. Если тип `Period` содержит массив событий (`events`), это означает, что все события для всех загруженных периодов хранятся в Redux-сторе. При большом количестве периодов или большом объеме данных внутри каждого периода это может привести к избыточному потреблению памяти и замедлению работы стора (так как любое обновление состояния вызывает пересчет селекторов).
- **Сценарий проявления:** При увеличении количества временных отрезков в системе или росте числа событий за один период объем данных в Redux будет расти линейно, что может привести к деградации производительности фронтенда.
- **Необходимые условия:** Наличие большого объема данных в массиве `events` внутри объектов `Period`.
- **Как исправить или проверить:** Рекомендуется рассмотреть возможность разделения состояния: хранить в `periodsSlice` только метаданные периодов и идентификатор активного периода, а сами события загружать в отдельный кэш или хранилище по запросу (при смене `currentPeriod`), чтобы не перегружать стор данными всех периодов одновременно.

## 2. Избыточная проверка типа массива в хелперах

- **Приоритет:** Low
- **Тип:** улучшение
- **Что обнаружено:** В функциях `getPeriodById` и `getPeriodIndexById` используется проверка `Array.isArray(state.periods)`, несмотря на то что в типе `AppState` поле `periods` строго определено как массив:
```text
type AppState = {
    pageTitle: string,
    currentPeriod: string,
    periods: Period[],
}
```
Цитата из хелпера:
```text
const getPeriodById: (state: AppState) => AppState['periods'][number] | undefined = (state) => {
    if (!Array.isArray(state.periods)) {
        return undefined;
    }
    return state.periods.find((period) => period.periodId === state.currentPeriod);
}
```
- **Почему это важно:** Это не является ошибкой, но создает избыточность в коде. TypeScript гарантирует, что `state.periods` является массивом на этапе компиляции. Такие проверки обычно имеют смысл только при работе с данными из внешних источников (API), которые еще не были типизированы или прошли через валидацию.
- **Сценарий проявления:** Увеличение объема кода без функциональной необходимости; потенциальное введение в заблуждение других разработчиков о том, что поле `periods` может принимать значения, отличные от массива.
- **Как исправить или проверить:** Удалить проверку `if (!Array.isArray(state.periods))`, так как тип `AppState` уже обеспечивает эту гарантию.
